# Пользовательские сценарии для проверки (Scheduling API)

Документ фиксирует основные пользовательские сценарии приложения бронирования
встреч для использования в ручном и автоматизированном (e2e) тестировании.
Источники правды: `project-spec.md`, `spec/*.tsp` (контракт API), реализация в
`apps/backend/src` и `apps/frontend/app`.

## Роли и ключевые правила

- **Владелец календаря (Owner)** — единственный предзаданный профиль, без
  аутентификации, работает в `/admin`-разделе фронтенда.
- **Гость (Guest)** — бронирует слоты без аккаунта, владеет своей бронью через
  `cancellationToken`, выдаваемый один раз при создании.
- **Окно записи**: 14 календарных дней от текущей даты, вычисляется по UTC-суткам
  (`apps/backend/src/common/scheduling/booking-window.ts:23-43`).
- **Правило занятости слота**: на одно и то же время нельзя создать две брони,
  даже для разных типов событий — проверка идёт по пересечению интервалов среди
  всех `accepted`-броней (`apps/backend/src/bookings/bookings.service.ts:61-71`,
  `apps/backend/src/slots/slots.service.ts:50-65`).
- **Удаление типа события** не удаляет и не блокирует существующие брони — они
  хранят снэпшот `eventTypeName`/`durationMinutes`
  (`apps/backend/src/storage/entities/booking.entity.ts:8-15`, `models.tsp`).
- Коды ошибок API: `ApiError { code, message }` (`spec/models.tsp`).

## Как использовать этот документ

- Для ручного QA: каждая строка таблицы — отдельный тест-кейс с явными шагами и
  ожидаемым результатом.
- Для e2e-автоматизации: колонка "API / код" даёт точку входа (эндпоинт, код
  ошибки, файл:строка бизнес-логики) для написания assert'ов.
- При изменении контракта (`spec/*.tsp`) или бизнес-правил в
  `apps/backend/src/common/scheduling/` и `bookings.service.ts` этот документ
  нужно обновлять синхронно.
